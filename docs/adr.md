# Architecture decision records

| ADR | Decision | Rationale / consequences |
|---|---|---|
| 001 | Separate .NET data/control planes | Gateway has no admin routes; Admin API never forwards inference bodies. Separate listeners/roles limit blast radius, but both use shared DB/Redis. |
| 002 | Vue + OIDC BFF, not browser bearer tokens | Secure cookie, code+PKCE, CSRF; IdP owns MFA. SameSite=Lax supports OIDC redirects. SaveTokens=false limits leakage; some IdPs ask logout confirmation. |
| 003 | Metadata-only accounting and masked audit | No prompt/response persistence, even for troubleshooting. Downstream legal case records stay in the approved case system; identifiers can still be personal/public-record data. |
| 004 | Virtual-key HMAC and certificate-protected DP credentials | Plain key shown once, pepper outside DB. DP key ring shared in DB and encrypted in production. Pepper/certificate loss requires recovery or key replacement. |
| 005 | Redis atomic reserve/reconcile | Shared rate/budget/circuit state and invalidation across services; restrict namespace/commands. In-memory mode is only for local/test environments. |
| 006 | JSON passthrough, data-driven provider/model profiles | New model families do not require a release. Rewrites/translation apply only supported fields; provider contract tests are still needed. |
| 007 | Rotation retains budget lineage | Immediate revoke default, optional 24h grace; both predecessors/replacements share spend so rotation cannot evade budgets. |
| 008 | File-based Aspire, Compose generated + mandatory override | Aspire is source of resource graph; approved override supplies deployment-specific TLS/ACL/roles/network/container controls. Never deploy base alone or containerize AppHost. |
| 009 | Production external IdP/provider; local test services only in run mode | Dev realm/FakeLlm/Vite are not production workloads. Production images contain static Vue assets served by BFF. |
| 010 | Accessibility design goal with explicit evidence boundary | Originally WCAG 2.2 AAA with four themes; since 2026-10-09 the target is WCAG 2.2 AA (24 px targets) with three themes (light, dark, Lumen). Contrast/component/browser automation; manual screen-reader/usability/IdP review needed, no automated certification claim. |
| 011 | Chiseled-extra and strict transport | Nonroot, no shell, ICU/time-zone data for Swedish budgets. HTTPS probes use a dedicated process mode; municipal PKI/secret delivery required. |
| 012 | Testcontainers integration fallback | File-based AppHosts are not supported by DistributedApplicationTestingBuilder. Real Postgres/Redis/Kestrel tests plus real-stack Playwright cover runtime behavior. |
| 013 | Routing rules use an in-house CEL-subset condition language and never widen access | Modelled on Bifrost. Conditions are written in a CEL subset implemented in `Domain` instead of a community CEL package: no new dependency or licence cost, no loops or side effects, linear-time regex (non-backtracking, literal patterns only), bounded length/depth, and positioned validation errors plus explain traces. Admin-authored expressions run on the request path, so the cost is bounded by expression size and budget/token lookups happen only when a rule uses them. Rules run after the PII policy and before candidate selection; provider allow-lists, residency, the PII on-prem restriction, endpoint kind and circuit state apply to whatever a rule chose, and rules cannot see credentials or prompt content. There is no silent return to the requested model: a matched rule whose models cannot serve the request fails with `no_eligible_provider`. |
| 014 | Rule ownership follows the organisation, but the user decides what happens when it changes | Rules are scoped to a key, team, department or globally (checked in that order, then by priority). Rules often belong to a service rather than the org chart, so deleting a team or department that has rules asks whether to **delete** them or **deactivate** them (default) until a new owner is assigned; deactivated rules are *orphaned*, cannot be enabled, and are reassigned explicitly. There is deliberately no foreign key (an orphaned rule never matches). A key-scoped rule follows the key through rotation, like budgets. Routes and models used by a rule cannot be deleted or renamed. Only global rules are exported/imported because ids differ between environments. |
| 015 | Data for other teams goes through interfaces, never the database; security events are pushed over OpenTelemetry | The gateway is open source and adopters run different databases, warehouses and SIEMs, and isolate services behind an integration layer. Security events are log records in the `Ume.LlmGateway.Security` category with stable event and attribute names; an adopter's OTel Collector routes them to any SIEM, so the gateway has no SIEM-specific code. Refused keys are counted per (reason, endpoint, key, client network) and flushed in bounded batches, because unauthenticated callers must not be able to grow the database; the presented key is never kept. BI and management get a separate read-only Data API (planned) with OAuth scopes per consumer class and incremental cursors. Retention, minimum group size and source-address detail are adopter settings with privacy-preserving defaults. See [data-access.md](data-access.md). |

| 016 | Old data is removed by one database function, and usage is summarised by month first | Retention is set in the admin UI (usage data and audit log separately, 90–3 650 days, default 365; audit may be kept for ever) and applied nightly by the admin API, which calls `ume_retention_step`. The function runs with the table owner's rights, so the admin role never gets `DELETE` on usage, refused-key, alert or audit rows: the audit log stays append-only for everything younger than the retention, and the 90-day minimum holds even against a direct database call. Usage goes in whole Europe/Stockholm months, after its monthly totals are written in the same transaction that moves the boundary (`UsageRetainedFrom`); readers take totals before the boundary and records after it, so budgets (whose long periods start on a month) and monthly reports stay exact. |

| 017 | Updates without downtime are opt-in, by instance replacement rather than in-place reload | Most installations run one instance, so `compose.prod.yaml` is unchanged; `compose.rolling.yaml` adds second gateway and admin API slots on their own host ports for the adopter's existing proxy, because adopters already run nginx, Nginx Proxy Manager or F5 and a bundled load balancer would duplicate it. Every service fails readiness on the stop signal and, for `Shutdown__DrainSeconds`, answers with `Connection: close` before closing its listener: a proxy retries a refused connection for any method but not a POST sent on a pooled connection the server closed, which measured as lost model calls without the drain. Connections the kernel accepted but the stopping instance never read are still reset, so the nginx example retries POSTs that failed before any response (`non_idempotent`), limited to 10 s so a long request is never repeated. Kubernetes gets Kustomize manifests rather than a Helm chart: plain YAML that adopters patch in their own overlays or GitOps repositories, no template language to maintain, and `kubectl` already includes it. Only backward-compatible migrations allow a rolling update, so every release states *Rolling update: yes/no*. |

| 018 | A request can lower its own residency ceiling with `x-ume-max-residency`, never raise it; a key can require the header | A key's allowed residencies are set by whoever manages the key and can be widened later, so a client that must keep some data on-prem or in the EU cannot rely on the key alone. Any key may send `x-ume-max-residency: OnPrem | Eu | External` (the `DataResidency` names, case-insensitive; no aliases and no numbers: omit the header for no ceiling). Anything else, an empty value or two values is `400 invalid_request`, because ignoring a malformed ceiling would fail open. A key with `RequireMaxResidency` refuses requests without the header, so a forgotten header fails instead of running without a ceiling. The ceiling is one more constraint in candidate selection, intersected with the key's residencies and the PII on-prem restriction after routing rules and fallback lists are worked out (ADR 013), and also before routing where the budget is reserved with the rate limit, so no rule, fallback, retry or token quota estimate goes above it. When no configured target within the ceiling exists the answer is `403 max_residency_not_met`; when such targets exist but are disabled or drained it is `503 no_eligible_provider` with `Retry-After`, so the caller waits instead of widening; failing targets fall back and answer 502/504 like any request, and there is never a silent fallback to a wider residency. It applies to every endpoint that reaches a provider, live sessions included, and `GET /v1/models` lists only what the ceiling allows. `x-ume-residency` keeps reporting where the request went; a caller that must be sure checks it, since an older instance ignores the header during a rolling update. Parsing is a span comparison and the intersection a lookup in eight shared arrays: no allocation, no extra round trip, and nothing changes for clients that do not send it. |

| 019 | Where a model processes data and where it is called are configuration of the model, resolved when the catalogue loads | One Azure AI Foundry resource holds global, data zone and regional deployments, and serves rerankers through their publisher's API (`…/providers/<publisher>/v2`) rather than the OpenAI v1 API, so neither a provider's residency nor its address describes every model under it. A model therefore has an optional residency of its own (null = the provider's), and a Foundry reranker a request address derived from its publisher (from discovery's `modelPublisher`, never a publisher list in code), with an optional address and authentication of its own, so a new reranker, a new publisher, a changed route or a model in a new location is set in the admin UI, never released (the user's requirement on #72). The gateway gives such a model a view of its provider when it loads the catalogue, as for Claude on Foundry: the same id, credential and switches (so health, circuit, usage, the credential cache and provider allow-lists stay the provider's) with the model's residency, address, authentication and capabilities. Routing, keys' residencies, the PII restriction, the residency ceiling (ADR 018), `/v1/models` and `x-ume-residency` read the model's provider as before, so they use the model's residency with no new code on the request path and no per-request work; models that look the same share one view. Because the provider's credential goes with it, a request address must be on the provider's own resource (checked by the admin API and again when the catalogue loads; another host is never called). Discovery suggests the kind, publisher and residency (from `sku.name`); the admin confirms them, since the residency is a classification the admin is responsible for. An older instance ignores the new columns during a rolling update, so a model's own residency is set only after every instance runs the release that reads it. |
| 020 | A platform is an integration; its credential keys can act as keys assigned to it, and an assigned key cannot be used directly | Supersedes the draft "a key can act for listed teams". Departments must pay for and limit their own chatbots on a shared platform. A key already carries everything that is wanted per chatbot (models, residency, PII, limits, budget, usage), so the chatbot's unit in the gateway is a key, made by the department's own admins and marked as used through the integration. The platform authenticates with a credential key and names the assigned key by id in `x-ume-on-behalf-of`; the request then runs as that key, so budgets, rules, policies, usage and reports need no new concept. An assigned key has no usable secret: nothing is copied into the platform, leaked or rotated per chatbot. Resolution is one in-memory lookup: no Postgres and no extra Redis round trip. The credential key's own allow-lists do not apply to acted requests; the grant is the assignment. |
| 021 | Integrations read configuration from the data plane and reports through a scoped Integration API on the control plane, with gateway keys; each setting has one owner | The Data API is optional and built for reporting, so requiring it for a platform's configuration was a wrong dependency. What a key may use (models with prices and limits, teams, assigned keys and their settings, features) is answered by the gateway from memory, so a platform shows the gateway's values instead of keeping copies. What queries the database (usage, budget status) is `/integration/v1` on the Admin API, keeping ADR 001; it accepts credential keys with per-key scopes, empty by default, so rotation, expiry, address lists and audit are reused and no second credential store exists. |
